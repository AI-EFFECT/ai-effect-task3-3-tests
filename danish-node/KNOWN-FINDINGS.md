# Danish node: known findings

These findings apply to frozen AI-EFFECT commit `e8914565e966a2d78879c314f980574769d31b87` and the 23 and 24 November 2026 closure runs on Docker under Windows.

| ID | Finding | Evidence | Impact | Recommended owner action |
|---|---|---|---|---|
| DK-SEC-01 | Danish control endpoints accept calls without a valid token as supplied. Each service only enforces a token when `SERVICE_API_KEY` is set in its own environment, and the supplied `docker-compose.yml` does not pass it. | Script 02: `/control/status` returned `404` (application reached) instead of `401` for missing and invalid tokens on all three services. | Anyone who can reach host ports 18101 to 18103 can start, poll or read tasks. | Pass `SERVICE_API_KEY` to the three services in the Compose file and document it in the onboarding guide. |
| DK-REL-02 | Overlapping workflows can return each other's outputs. The orchestrator derives task IDs from the node key only, so every workflow from the same blueprint reuses the same task IDs, and each Danish service stores task state in memory keyed by task ID alone. Overlapping workflows can also fail with "Task not complete" when one workflow's task record is overwritten by the other's running job. | Script 25: task IDs identical across workflows; outputs belonged to the other workflow in 3, 1, 3, 3 and 1 of 3 rounds across five executions. In one execution, the first workflow failed in 2 of 3 rounds with `HTTP 400: {"detail":"Task not complete"}`, at the topology step in one round and the drawing step in the other. Root cause in `orchestrator/src/services/workflow_engine.py` (`_task_id_from_node_key`) and `common/concurrent.py` (`TaskManager`). | Any concurrent use, including Task 3.4 parallel measurements, can deliver another run's results while reporting success. | A fix is in progress as part of the WP3 orchestrator reliability work. Rerun script 25 to confirm it before any concurrency or load testing. |
| DK-VAL-01 | Unrecognised terminals are silently dropped, and missing ones are replaced by defaults. Names must match the built-in list exactly, including capitals; anything else is discarded. If no supply or load remains, `310-D::CHP` or `716-D::Dumpload` is substituted with a warning. If at least one valid name remains, a misspelt one is dropped with no warning. The run configuration is always marked `valid: true`, and nothing downstream reads that field. | Script 20: an empty request and an unknown supply completed using the defaults. Direct checks of the config assistant's own functions: a misspelt load (`330-D::Heat dumplod`) became `716-D::Dumpload`; lowercase names were not recognised; a misspelt second supply was dropped with no warning. Live portal, 24 November 2026: the prompt "feed the heat dumpload at 311-d" (a switchboard that does not exist) completed with `716-D::Dumpload`, a warning and `valid: true`. | A user can receive topologies for a plant or load they did not request, presented as valid. Setting `valid: false` alone would not stop the workflow, because no service or the orchestrator checks it. | Reject requests that contain unrecognised terminals, with a message listing the valid options, or require confirmation before defaults are used. Match names regardless of capitals. If `valid` is kept, make the topology generator stop on `valid: false`. |
| DK-LLM-01 | On the prompt route, the model converts the text to JSON but also adds settings the prompt does not mention, although its instructions say to omit such fields rather than guess. The guesses vary between runs and replace the service defaults (`allow_hx: true`, `allow_bypass: false`, `max_extra_pipes: 1`, `load_topology: any`). With a single load, the guessed `load_topology` has no effect, because single-load designs are always kept; the guesses that change the result are `allow_hx`, `max_extra_pipes` and `allow_bypass`. | Windows, 23 and 24 November 2026, same prompt in 15 runs (5 single runs, then script 12 twice with 5 rounds): the defaults were used in 0 of 15. `max_extra_pipes` was 0, 2 or 3, `load_topology` was series or parallel, and `allow_bypass` was sometimes true. One run set `allow_hx: false`, and its workflow failed with "no feasible topology found" with no warnings and no recorded assumptions; the same settings as structured input fail the same way, and switching the heat exchanger back on gives 4 topologies. | The same request can succeed, return a narrower or different set of topologies, or fail, and the user is not told that settings were guessed. | Keep only the fields the prompt mentions, or discard model-supplied settings that the user did not request; consider a larger model or examples in the instructions; ask the user to confirm extracted settings (the output already sets `user_confirmation_required: true`, but nothing acts on it). |

## Recorded observations, not confirmed defects

- **DK-REL-01:** each service holds task status in process memory. A restart between runs recovered correctly (script 24), but a restart during a run would lose that task's status. Not tested.
- Unknown reference protocols are rejected by the orchestrator at submission with HTTP 400, before any service is called.
- The supplied integration notes mention four SVG drawings for the example request. The frozen generator returns 20 candidates and 20 drawings (its default limit), with a recommended candidate that is not guaranteed to be globally optimal.
- Repeated structured runs produced identical candidate networks, so the structured route appears deterministic for this fixture.
- Orchestrator tasks expose only `created_at` and `updated_at`. Queue time cannot be separated from execution time.
- Ambiguous prompts are resolved by the model without recording the assumption. Live portal, 24 November 2026: "feed the heat dumpl0" (misspelt, no switchboard) returned `716-D::Dumpload` with empty `warnings` and `assumptions` and `valid: true`.
- Ollama is started by Docker Compose next to the services, not by the services or the portal. If it is unavailable, the config assistant waits up to 240 seconds (`OLLAMA_TIMEOUT`), records a warning and falls back to the default terminals.
- Services added to the Danish node after commit `e8914565e966a2d78879c314f980574769d31b87`, or deployed only on the hosted platform, are outside this baseline.
